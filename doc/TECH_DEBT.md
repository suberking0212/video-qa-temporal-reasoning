# 技术债务格式与维护规范

本文件只登记已经存在并有证据的工程质量、可靠性、性能、安全或维护性问题。新功能愿望和尚未实现的 PRD 需求不是技术债务；功能是否完成由 PRD 和 `PROGRESS.md` 跟踪。

## 维护规则

1. 每条债务分配永久唯一 ID：`TD-001`、`TD-002`……关闭后不复用、不删除，以保留决策历史。
2. 新条目必须说明复现证据或观察依据、实际影响、当前规避办法和可判定的解决标准。只有“代码不够优雅”而无影响/风险说明，不足以登记为债务。
3. 状态统一为：**Open**（待处理）、**Accepted**（明确接受风险并定期复核）、**Planned**（已排入近期工作）、**In Progress**（处理中）、**Resolved**（已解决并验证）。状态变化时更新条目中的变更记录。
4. 优先级统一为：
   - **P0**：安全、隐私、数据丢失/串数据，或阻断首版核心验收的问题。
   - **P1**：显著影响核心质量、可靠性或目标性能，但有临时规避方式。
   - **P2**：中等维护/性能问题，短期有可接受的规避方式。
   - **P3**：低风险改进，当前对用户和验收影响很小。
5. 每项债务应引用相关 PRD ID（若有）及进度记录日期/里程碑。优先级不能只按实现难度排列，应按用户影响、发生概率和后果判定。
6. 只有达到“解决标准”且有新的验证证据时才能标为 Resolved。已接受的债务要写明接受理由和重新评估触发条件；不设无依据的承诺日期。
7. 如果债务揭示 PRD 目标本身不合理，应先更新 PRD 并记录理由，不能通过降低实现标准来悄悄消除债务。

## 单条债务模板

### TD-XXX — 简短、具体的问题标题

- **状态 / 优先级：** Open / Accepted / Planned / In Progress / Resolved；P0 / P1 / P2 / P3
- **发现日期 / 影响模块：** YYYY-MM-DD；模块或处理阶段
- **关联 PRD：** 需求 ID；无直接关联时写“无”
- **问题与证据：** 可复现步骤、测试结果、日志或测量数据；避免只写判断
- **影响与风险：** 影响哪些用户行为/验收指标，以及可能后果
- **当前规避方式：** 无则写“无”
- **处理触发条件 / 解决标准：** 可判断是否应该处理、何谓解决
- **状态变更记录：** YYYY-MM-DD：状态变化、理由及验证证据；新增时记录“登记”

## 示例标题命名

- `TD-001 — 长视频 OCR 阶段耗时超过首版预算`
- `TD-002 — 低置信度事件仍可能进入确定性回答`

示例仅说明标题格式，不代表项目中已经存在这些问题。不得把示例当作真实债务登记。
