- **MUST / 必须**：首版交付必须满足的要求。

- **MAY / 可以**：可选能力，不影响首版验收。
- 需求 ID（如 `FR-QA-001`）一经分配不得复用或因重排而改变。进度和技术债务记录引用需求 ID，不复制需求正文。
- `P0` 为首版范围；`P1` 为有价值但不阻塞首版验收；`P2` 为明确不纳入首版的后续方向。

## 2. 产品概述

### 2.1 一句话定位

帮助用户从已处理的视频中检索事件、理解事件的时间关系，并得到带有可核验视频证据的答案。

### 2.2 用户问题

用户观看长视频时，往往知道自己想找什么，却难以快速定位相关片段；普通关键词检索也难以回答“谁先做了什么”“某动作持续多久”或“某事件之后发生了什么”。单纯生成自然语言答案还可能掩盖模型的不确定性，无法让用户核对结论。

### 2.3 目标用户与首要场景

- **首要用户**：需要查找、复习或整理教学/讲解类视频内容的学生、教师和研究者。
- **首要场景**：用户导入一段预先录制的视频，等待系统完成处理，用自然语言提问；系统返回简洁答案、相关时间段和证据，用户可跳转原视频核验。
- **首版语言**：界面与主要交互使用中文。具体支持的语音、字幕和提问语言由首版实现明确列出；未列出的语言不作准确性承诺。
- **产品化范围说明**：教学/讲解类视频是首版验证场景，不是产品永久边界。后续扩展会议、访谈、影视、体育、监控或产品演示等类型时，沿用统一的 `Observation`、`Event`、`Evidence` 数据契约，但允许使用不同的采样、模态提取、事件模式、检索和推理策略；不同类型必须独立评测，不承诺共享相同精度或处理成本。

### 2.4 产品目标

1. 建立从视频导入、处理、提问到证据核验的完整闭环。
2. 支持视频内容检索及基础时序问题，而不只对整段视频做无证据摘要。
3. 让回答能够追溯到原视频中的一个或多个时间段；证据不足时明确表达不确定性。
4. 采用可替换的开源或可商用组件优先策略，为未来的领域扩展、私有化部署和商业化验证留出空间。
5. 通过可复现的测试集和质量指标验证功能，不以单个演示视频的成功作为系统有效性的唯一依据。

### 2.5 首版非目标

以下能力不属于首版验收范围：

- 实时直播、低延迟流式视频理解或实时告警。
- 对任意领域、任意语言、任意视频类型作准确性保证。
- 视频编辑、生成、自动剪辑或社交分享。
- 多租户 SaaS、计费、企业 SSO、复杂组织权限及商业级 SLA。
- 从零训练基础视觉、语音或语言模型。
- 依靠无证据的模型常识补全视频中没有出现的信息。

这些方向可在后续版本评估，但不得作为首版交付的隐含承诺。

### 2.6 首版产品形态

首版采用“**可复现的 CLI/API 核心 + 薄 Web Demo 展示层**”的产品形态，不将 Web 页面作为业务逻辑的唯一承载。

- **核心层（P0）**：视频导入、处理、提问、评测和结果导出必须能够通过 CLI 或稳定的 Python/API 接口独立运行。核心输出至少包括答案、证据时间段、来源、不确定性、处理耗时和错误状态。
- **展示层（P0）**：提供轻量 Web Demo，覆盖上传视频、查看处理状态、播放视频、输入问题、展示答案和点击证据跳转等主流程。
- **复用要求（P0）**：CLI、API 和 Web Demo 必须调用同一套核心模块、领域对象和证据契约。不得在前端回调中重新实现视频处理、模型调用、检索或时序推理。
- **优先级（P0）**：核心处理可靠性、评测可复现性和证据可解释性优先于页面视觉效果。

首版不要求登录、多租户、计费、复杂权限、实时直播、视频编辑或完整后台管理。Web Demo 是核心能力的可视化入口，不是独立的产品实现。

## 3. 用户流程

### 3.1 主流程

1. 用户选择或导入本地视频。
2. 系统校验媒体能否读取，并展示视频名称、时长及当前处理状态。
3. 系统异步完成所需的媒体解析、语音/画面信息提取和索引构建；用户可以看到处理中、已就绪或失败状态。
4. 用户选中已就绪的视频并输入问题。
5. 系统返回答案、一个或多个证据时间段及不确定性提示（如适用）。
6. 用户点击证据时间段，播放器跳转到对应位置并可继续播放原视频。

### 3.2 异常流程

- 无法读取或不支持的视频：说明失败原因或可采取的修正方式，不创建一个看似可用的索引。
- 视频仍在处理：提示用户等待，不将未完成索引伪装成完整结果。
- 处理失败：展示失败阶段和可理解的错误信息；允许用户在必要时重新发起处理。
- 问题含糊、超出首版支持范围或没有足够证据：请求澄清，或明确表示无法从当前视频证实，不生成确定性结论。
- 单个模型或处理组件失败：保留可诊断的错误状态；若部分结果可用，必须标注其不完整性。

## 4. 功能需求

### 4.1 视频导入与处理

#### FR-VID-001 导入视频（P0）

用户必须能够选择一个本地视频作为问答对象。系统必须在处理前校验输入可读取，并向用户说明首版支持的容器、编码和大小限制。遇到不支持或损坏的文件时，系统必须给出可理解的反馈。

**验收标准：** 有效视频可以进入处理流程；无效或不支持的视频会被拒绝并显示原因；不产生误报为“处理完成”的记录。

#### FR-VID-002 展示处理状态（P0）

系统必须为每个视频展示至少以下状态：等待处理、处理中、已就绪、失败。处理中和失败状态应尽可能说明当前阶段或错误类别。

**验收标准：** 用户能够区分正在处理、可提问和处理失败的视频；刷新或重新打开界面后状态不会无故变成已就绪。

#### FR-VID-003 处理结果与视频关联（P0）

转写、画面观察、事件、索引及后续答案必须关联到其来源视频。系统不得把一个视频的证据展示为另一个视频的证据。

**验收标准：** 对至少两个不同视频依次提问，答案中的视频标识和时间段始终指向当前所选视频。

### 4.2 问答、时序推理与证据

#### FR-QA-001 对已就绪视频提问（P0）

用户必须能够针对当前选中的已就绪视频输入自然语言问题。系统应优先支持中文提问。对尚未就绪的视频，系统必须提示其当前不可问答。

#### FR-QA-002 返回带时间定位的证据（P0）

每个确定性回答必须返回至少一个关联证据片段。每个片段至少包含视频标识、起始时间、结束时间和可用于用户核验的证据描述或来源类型。内部时间表示统一使用毫秒整数；界面可按易读格式显示。

**验收标准：** 用户可从答案打开相应视频位置；起止时间位于视频有效时长内，且证据描述与返回答案相关。没有证据片段的回答不得标记为已证实答案。

#### FR-QA-003 证据不足时拒答（P0）

当检索或推理证据不足以支持结论时，系统必须明确表达无法确认，并可指出需要补充的信息或建议用户查看的候选片段。系统不得仅凭模型常识将推测表述为视频事实。

**验收标准：** 对评测集中明确没有答案、证据缺失或内容不可辨识的问题，系统可以返回不确定/无法确认状态；不能通过编造时间戳或证据来满足回答格式。

#### FR-TIME-001 事件先后关系（P0）

系统必须支持首版范围内的事件顺序类问题，包括“某事件之前/之后发生了什么”及“多个可识别事件的先后顺序”。回答应指出用于判断顺序的证据时间段；时间重叠或无法可靠区分先后时必须说明不确定性。

#### FR-TIME-002 次数与持续时间（P0）

系统必须支持对可识别事件进行基础次数统计和持续时间估计。回答必须与证据片段对应；当事件边界不清、画面遮挡或证据不足以可靠计数时，系统必须说明估计或限制，不得伪装为精确测量。

#### FR-QA-004 澄清与范围提示（P1）

对指代不明、条件冲突或明显超出首版支持范围的问题，系统应请求澄清或指出限制，而不是静默地把问题改写成另一个问题。

#### FR-QA-005 答案与证据可区分（P0）

界面必须区分模型给出的答案、观察到的证据及其不确定性。证据来源至少能区分语音/字幕、画面文字、视觉观察或其他实际使用的来源；未启用或不可用的来源不得伪称已验证。

### 4.3 错误处理与数据控制

#### FR-ERR-001 处理失败可见（P0）

媒体解析、索引或推理失败时，系统必须向用户显示失败状态，并保留足以诊断问题的错误类别或日志标识。不得静默返回空答案或沿用其他视频的缓存结果。

#### FR-DATA-001 删除视频及衍生数据（P0）

用户必须能够删除一个视频及其可识别的衍生数据，包括转写、抽取结果、事件、索引和相关缓存。删除完成后该视频不得继续参与检索或问答。

**验收标准：** 删除后重新搜索或提问不会返回该视频的结果；若物理清理为异步任务，界面应显示删除状态，且删除中的内容不可继续用于问答。

### 4.4 CLI/API 与 Demo

#### FR-APP-001 CLI 核心命令（P0）

系统必须提供可脚本化的 CLI，至少支持视频导入、处理、状态查询、提问和评测。CLI 应能在没有 Web 页面时完成核心处理和问答，并返回机器可读结果或稳定的结构化输出。

**建议命令：**

```text
videoqa ingest <video>
videoqa process <video_id>
videoqa status <video_id>
videoqa ask <video_id> "问题"
videoqa evaluate <dataset>
```

**验收标准：** 在干净环境按文档执行 `ingest → process → ask` 可以完成核心流程；问答输出包含答案、证据时间段、来源、不确定性和错误状态；评测命令能输出固定数据集的结果。

#### FR-APP-002 统一核心接口（P0）

CLI、API 和 Web Demo 必须复用同一套核心处理模块和领域数据契约。页面层不得直接拼接模型提示词、操作底层文件或实现时序关系。

**验收标准：** 对同一视频和同一问题，通过 CLI 与 Web Demo 获得的答案、证据来源和时间范围遵循同一数据结构；替换展示层不需要修改媒体处理、检索或时序推理逻辑。

#### FR-APP-003 薄 Web Demo（P0）

系统必须提供轻量 Web Demo，支持上传视频、查看处理状态、播放视频、提交问题、展示答案与证据，并支持点击证据跳转到视频时间点。

**验收标准：** 用户可以在不使用命令行的情况下完成主流程；至少覆盖一个有效流程和一个失败/证据不足流程；页面显示的处理状态、答案和错误信息来自统一 API 或核心服务，而不是静态演示数据。

### 4.5 多类型视频扩展（P1/P2）

以下需求不属于首版 P0 验收，但用于约束后续产品化方向；新增类型前必须先建立该类型的数据样例、问题集和验收口径。

#### FR-ROUTE-001 视频类型策略配置（P1）

系统应允许为视频选择或配置解析策略，例如 `lecture`、`meeting`、`film`、`sports`、`surveillance`、`product_demo` 和 `generic`。首版可以由用户手动选择；自动识别不属于首版要求。

#### FR-ROUTE-002 类型专用解析链路（P1）

每个已启用的视频类型可以配置独立的采样策略、ASR/OCR/说话人识别/目标跟踪开关、事件模式、检索权重和答案策略，但所有链路必须输出统一的观察、事件和证据对象。

#### FR-ROUTE-003 模型与策略可追溯（P1）

回答和索引必须记录实际使用的类型策略、模型/权重版本、采样参数和处理阶段版本，以便重建、比较和回滚。

#### FR-ROUTE-004 按类型评测（P1）

新增类型必须独立报告答案正确率、证据命中率、拒答率、延迟和处理成本；不得用教学视频评测结果代表其他类型的产品质量。

#### FR-ROUTE-005 自动类型识别与路由（P2）

当已积累足够多类型样本并证明手动策略可稳定工作后，系统可以自动预测视频类型并选择策略。误判时必须允许用户覆盖，且错误路由不得导致数据或证据串用。

## 5. 质量属性与验收目标

下列指标用于首版验收。测量结果必须同时记录评测集版本、运行环境、模型/组件版本和测量方法。若基准环境下无法达标，应先定位并记录差距，再经 PRD 变更评审调整目标，不得只删掉失败指标。

### 5.1 问答质量（P0）

- 建立至少 **50 条人工核验的问题样例**，覆盖至少 3 个视频及首版支持的主要问题类别；保留标准答案、证据时间段和数据来源，其中至少 20 条作为独立验收子集，不参与提示词或参数调试。
- **答案正确率**：在独立验收子集上按问题逐条人工判定正确/不正确，整体正确率目标不低于 **70%**；同时按问题类别报告，避免总体分数掩盖某类系统性失败。
- **证据命中率**：对有明确时间标注的问题，若至少一个返回片段与任一标注片段的时间交并比（tIoU）不低于 **0.3**，则计为命中；总体命中率目标不低于 **70%**。无法可靠标注边界的问题应从该指标中单独列出并说明，不得静默删除。
- **证据不足处理**：独立验收子集中应至少包含 10 条无答案或证据不足样例；对此类样例，系统不得以确定性事实回答，正确拒答比例目标不低于 **80%**。同时报告有答案样例的错误拒答比例。

### 5.2 性能（P0）

- 在已完成索引的视频上，端到端问答延迟（从提交问题到答案和证据均可展示）目标为 **p95 不超过 15 秒**，以至少 30 个固定问题测量。
- 对 **10 分钟视频**，首版处理时间目标不超过 **30 分钟**。测试必须使用记录了 CPU、内存、GPU（如有）、模型和运行配置的参考环境，并分别记录预处理阶段耗时。
- 性能测试不得混合首次模型加载与稳态请求而不加说明；同时报告 p50、p95、失败数和资源峰值。硬件变化后应重新建立基线，但不因此自动改变产品验收目标。

### 5.3 可靠性与可诊断性（P0）

- 每个处理任务必须能最终进入已就绪或失败状态；不得无限期保持处理中而没有可诊断记录。
- 关键处理阶段必须记录阶段状态、耗时和错误类别。日志默认不得包含不必要的完整视频内容、敏感转写或密钥。
- 同一失败不得通过隐式使用过期或其他视频的结果来伪装成功。

### 5.4 可扩展性（P0）

- 媒体解析、语音/画面提取、检索、时序推理和答案生成应保持清晰职责边界，允许替换实现；替换某个组件时，不应要求重写用户流程和证据数据契约。
- 优先复用经过维护的开源项目和成熟模型/库；只有当现有组件无法满足明确需求时，才实现自有算法，并记录理由和评测证据。
- 可替换性不等同于首版必须接入多个供应商，也不要求过早建设插件市场或复杂微服务。

## 6. 数据与系统边界

### 6.1 核心概念

- **视频（Video）**：用户导入的原始媒体及其元数据。
- **片段（Segment）**：视频中的一段连续时间范围。
- **解析策略（VideoProfile）**：面向某类视频或任务的一组版本化配置，决定采样、启用的模态处理器、事件模式、检索和推理策略；它不是模型本身。
- **观察（Observation）**：从音频、字幕、画面或 OCR 等来源提取的信息，并保留时间范围和来源类型。
- **事件（Event）**：对主体、动作、对象及时间范围的结构化描述；可带置信度，不应被视为无误事实。
- **证据（Evidence）**：回答所引用的观察或片段，必须能追溯到原视频时间。
- **回答（Answer）**：自然语言结论、证据引用和不确定性状态的组合。

上述概念是产品层数据契约，不强制采用特定数据库、向量库或序列化协议。时间信息必须统一、可比较，并能映射回原视频。

### 6.2 系统边界

- 输入为用户有权处理的预录制视频及其可用音轨/画面；本产品不负责确认视频版权归属。
- 外部模型、第三方 API 和云服务均视作独立数据接收方，必须适用第 7 节的数据传输要求。
- 首版按单用户/单机或单项目使用场景设计；未来多租户能力不属于首版承诺，但模块边界和数据关联不得依赖全局共享状态。
- 原始视频、可重建的衍生结果和用户问题应能分别识别，以便删除、重新处理和诊断。

## 7. 安全、隐私与开源合规

### 7.1 隐私与数据使用

- 默认部署必须可在本地完成核心处理，不得在用户不知情时将视频、音频、转写或问题发送到外部服务。
- 如用户或部署管理员显式启用外部服务，界面或部署说明必须说明接收方、传输的数据类别及其用途。未配置外部服务时，不得让核心流程依赖其 API 才能运行。
- 视频和衍生数据仅用于该用户发起的处理与问答；不得默认用于训练、公开展示或跨用户检索。
- 仓库不得包含真实用户视频、访问密钥或未授权数据。测试数据必须说明来源及使用条件。

### 7.2 输入安全

- 视频字幕、OCR、语音转写及其他从视频提取的文本必须作为不可信内容处理，不能覆盖系统指令或授权边界。
- 用户输入和媒体解析失败均应作为正常错误路径处理；不得因解析媒体内容而执行其中携带的命令或外部操作。

### 7.3 开源与商业可用性

- 开源优先，但“开源”不自动代表允许商用。交付前必须核查直接依赖、模型代码、模型权重和数据集各自的许可证及用途限制。
- 引入新的模型或关键依赖前，应记录名称、版本/来源、许可证、用途限制和是否允许商业使用。许可证不清楚或限制与预期冲突时，不得将其作为商业化方案的默认依赖。
- 不得将权重、语料或用户数据提交进版本库，除非其分发许可和必要授权明确允许。
- 具体许可证清单与供应链扫描属于发布检查的一部分；不得仅凭项目主页的简介作出商用许可判断。

## 8. 发布验收与完成定义

首版只有在以下条件全部满足后才能标记为完成：

1. 用户可完成导入、处理、提问、查看证据并跳转原视频的主流程。
2. FR-VID、FR-QA、FR-TIME、FR-ERR 和 FR-DATA 中标记为 P0 的需求有可复现的验收证据。
3. 已建立并记录评测集；报告答案正确率、证据命中率、证据不足处理、问答延迟和视频处理耗时。未达目标的项目必须明确标为未达标，不得以演示成功替代。
4. 删除视频及衍生数据的行为已经测试；外部数据传输行为及默认配置已经验证。
5. 有效视频、无效视频、无答案问题、处理失败和时序关系问题均至少有自动化或可重复的人工测试流程。
6. 所有用于交付的关键依赖、模型与数据来源完成许可证核查；运行方式、已知限制和必要配置对用户可见。
7. 尚未解决且影响 P0 验收、安全、隐私或数据完整性的技术债务已显式列出；不得将其隐藏为“后续优化”。

## 9. 关键假设与复审触发条件

本初版基于以下假设：首要用户以中文交互；视频是预先录制且用户有权处理；首版以课程项目规模完成单用户闭环；采用成熟开源组件优先，必要时允许用户明确启用外部服务。

当出现以下情况时，应评估并更新本 PRD：首要用户或使用场景改变；需要默认云端处理；新增用户/组织隔离或数据保留承诺；主要问题类别从离线视频时序问答扩展；评测数据表明现有质量目标或定义不能反映真实使用价值；或商业化目标要求新增安全、审计、部署及 SLA 承诺。

## 10. 首版技术基线与实施计划

本章是当前首版的**默认实现基线**，用于指导开发顺序、降低重复选型和重复造轮子。它不改变前文的产品需求和用户承诺。只要不改变用户可观察行为、数据边界和验收口径，组件可以替换；替换理由、验证结果和影响应记录在 `PROGRESS.md`，产生的遗留问题登记在 `TECH_DEBT.md`。

### 10.1 技术选型原则

选型按以下顺序考虑：

1. 满足本 PRD 的产品行为和验收标准。
2. 优先采用成熟、维护活跃、文档完整的开源项目和现成模型，不自研已有通用能力。
3. 首选可本地运行、可私有化部署且许可证和模型权重用途清晰的方案。
4. 优先选择有标准接口、可独立替换的组件，避免业务层绑定单一供应商。
5. 以可观测的实际基准选择性能方案，不以模型参数量或宣传指标代替评测。
6. 先使用一体化程度适中的方案；只有规模、可靠性或团队协作确实需要时，才引入更重的基础设施。

每次引入新的关键组件前，应核查：版本和来源、许可证、是否允许预期的商业使用、运行资源、中文/视频场景表现、维护状态、替换成本和数据是否会离开本地。许可证不清楚、默认要求上传用户数据或无法通过最小基准测试的组件，不作为默认依赖。

### 10.2 首版默认技术基线

| 层次 | 默认选择 | 复用方式与理由 | 可替代方案/复审条件 |
|---|---|---|---|
| 媒体解析 | FFmpeg、ffprobe；Python 侧用 PyAV 或等价封装 | 复用成熟编解码、时长读取、抽帧和音频提取能力；统一以毫秒时间轴回写结果 | 仅在目标格式或部署限制无法满足时替换；不得重新实现通用解码器 |
| 场景与关键帧 | PySceneDetect + 可配置的关键帧采样 | 复用已有场景切分算法，降低逐帧推理成本 | 场景边界质量不足时增加内容感知采样或二阶段密集分析，不直接改写时间契约 |
| 语音识别 | `faster-whisper` + Whisper `large-v3`/`turbo` 作为候选基线 | 本地时间戳转写；通过适配器隔离模型版本和推理后端 | FunASR（如 Paraformer/SenseVoice）作为中文对照；以 WER、时间戳、速度和资源实测决定，不预设单一赢家 |
| OCR | PaddleOCR（PP-OCR 系列） | 复用中文 OCR，输出文字、置信度、区域和时间/画面来源 | 课件复杂版面可评估 PaddleOCR-VL 或其他文档/视觉语言模型；仅在 OCR 误差确实影响问答时增加 |
| 文本/视觉特征 | BGE-M3（文本）+ SigLIP/OpenCLIP（关键帧）适配器 | 分开处理文本召回和关键帧跨模态召回，避免每次查询都调用生成模型 | 根据 Recall@K、中文术语表现、资源和许可证替换；模型版本不写入业务逻辑 |
| 视频理解/事件候选 | VideoChat3-4B、Qwen3-VL 系列作为本地候选；InternVideo3-8B-Instruct 作为长时域候选 | 用于候选观察、片段理解和证据归纳；通过统一适配器和相同评测比较 | Gemini 视频理解作为显式启用的云端质量/能力对照；是否采用取决于数据传输、成本、延迟、许可和独立集表现 |
| 事件抽取与时序 | 通过结构化输出适配器调用已通过基准的视频模型，再由程序规则验证 | 模型抽取候选主体/动作/对象/证据；`temporal` 模块计算关系和统计 | 可更换 VLM/LLM；不得取消来源、时间和置信度字段，也不得让模型取代确定性时序计算 |
| 本地模型服务 | 开发期可用 Transformers；稳定运行优先评估 vLLM 或 SGLang | 复用批处理、量化和并发能力，避免自行编写推理服务 | 受硬件、模型架构或部署限制时替换；必须保持模型适配器和超时/错误契约 |
| 语言/多模态模型 | 默认使用经过版本和许可证核查的中文可用开放权重模型；通过 `ModelProvider` 接口接入 | 不把具体模型版本写死，便于本地、私有化和云端方案切换 | 仅根据评测质量、延迟、显存、许可证和数据传输要求切换，不以单次演示决定 |
| 持久化与向量检索 | PostgreSQL + pgvector + PostgreSQL 全文检索 | 一个成熟数据层同时保存业务实体、时间元数据、全文和向量，减少首版基础设施数量 | 数据规模或并发明确超过基线后再评估 Qdrant/Milvus/专用搜索引擎；迁移前须有基准和回滚方案 |
| 源视频/衍生文件存储 | 首版本地文件存储 + `StorageProvider` 适配器 | 单机首版少一个服务依赖；通过存储接口隔离路径、上传、读取和删除，避免业务逻辑绑定本地路径 | 需要多机、对象生命周期管理或云部署时，再选 S3 兼容存储；选型前核查许可证、服务条款、数据驻留和迁移能力。MinIO 等具体实现须通过该核查后才可作为部署选项 |
| 异步任务 | Celery + Redis | 复用成熟任务队列和重试能力，适合首版视频处理流水线 | 工作流分支、长任务补偿和多服务协同显著复杂后再评估 Temporal；不提前引入复杂编排 |
| 后端 API | FastAPI + Pydantic | 复用类型校验、OpenAPI 和异步接口能力；统一请求、响应和错误契约 | 仅在部署约束或团队既有能力明显要求时替换；保持 API 契约版本化 |
| 前端 | Next.js + TypeScript | 复用成熟 Web 生态，适合视频播放、任务状态、证据跳转和后续产品化 | 若课程演示需要极简原型，可短期使用轻量 UI，但核心逻辑不得写死在页面层 |
| 测试与评测 | pytest + 固定 JSONL 评测集；前端关键流程使用 Playwright 或等价工具 | 复用通用测试工具，确保问题、答案、证据和性能结果可重复 | 评测规模扩大后可接入 MLflow/DVC 等工具；首版不为工具本身增加流程负担 |
| 可观测性 | 结构化日志、阶段耗时和错误分类；再接入 OpenTelemetry/Prometheus/Grafana | 先满足诊断和性能验收，再按部署规模增加指标平台 | 当出现多进程、多机或长期运行需求时升级；日志不得泄露视频和密钥 |
| 本地开发与交付 | Docker Compose + `.env.example` + 明确的启动/迁移/测试命令 | 复用容器化环境降低“在我机器上能运行”的风险，便于课程展示和后续部署 | 需要弹性扩缩容时再评估 Kubernetes；不以首版复杂部署替代核心功能 |

### 10.3 按开发阶段接入的模型与工具候选

本节给出“先接入什么、为什么、何时替换”的候选顺序。它不是承诺所有模型都要接入，也不是以模型名称替代评测。每个模型都必须通过适配器接入，并记录权重、代码、运行时和许可证的独立状态。模型能力描述以官方资料为依据；“支持小时级/长视频”不等于对任意视频都能稳定精确定位事件。

#### 阶段 0：基线与选型验证

阶段 0 不急于部署最大模型，先准备可替换的候选集和最小基准。以下均为候选，不预设最终胜者：

| 能力 | 首选候选 | 对照/备选 | 选型说明 |
|---|---|---|---|
| 中文 ASR | `faster-whisper` + Whisper `large-v3`/`turbo`，另测适合当前硬件的较小规模 | FunASR Paraformer/SenseVoice | 比较中文词错率、时间戳偏差、处理速度和峰值资源；ASR 是课程视频的第一优先级 |
| OCR | PaddleOCR PP-OCR | Tesseract 或其他许可清晰的 OCR；复杂版面再评估 PaddleOCR-VL | 比较课件/字幕小字识别、中文术语和抽帧成本；OCR 结果必须带来源时间 |
| 文本向量 | BGE-M3 | E5/BGE 其他中文或多语种版本 | 比较转写片段 Recall@K、中文术语和资源占用；不直接用生成模型替代向量检索 |
| 视觉向量 | SigLIP/OpenCLIP 类模型 | 其他许可清晰的跨模态 Embedding | 用于关键帧召回和重排；先验证课程课件、人物和物体检索，不把它当作完整视频推理模型 |
| 视频/多模态模型 | VideoChat3-4B；Qwen3-VL 的可部署规模 | InternVideo3-8B-Instruct；云端 Gemini 作为非本地对照 | 只在固定问题和固定片段上比较事件抽取、证据描述、中文能力和显存；云端结果必须标注为外部服务对照 |

**阶段 0 退出规则：** 至少完成一组 ASR、OCR、向量模型和两个视频模型候选的最小基准；记录质量、延迟、峰值资源、许可证/权重来源和是否需要外部数据传输；未通过许可证或数据边界核查的候选不得进入默认方案。

#### 阶段 1：媒体导入与时间轴

阶段 1 不需要视频大模型。使用 FFmpeg/ffprobe、PyAV、PySceneDetect 和基础采样即可。模型只在场景边界质量不足时参与“内容感知采样”的实验，不得让大模型成为媒体导入的硬依赖。

#### 阶段 2：多模态观察与证据底座

推荐接入顺序：

1. **ASR：** `faster-whisper` 作为首个可运行基线；中文质量或部署效率不足时，用 FunASR 做对照。优先保存词/句级时间戳，而不是只保存整段摘要。
2. **OCR：** PaddleOCR 作为首选；对幻灯片、板书、字幕分别记录采样区域和识别置信度。
3. **视觉描述/事件候选：** 先使用 VideoChat3-4B 或实际硬件可承受的 Qwen3-VL 规模；若需要更强长时域和证据累积，再评估 InternVideo3-8B-Instruct。模型只生成候选观察，事件字段和时间范围必须经过程序校验。
4. **视觉向量：** SigLIP/OpenCLIP 用于关键帧召回；不要让生成式模型承担所有重复 Embedding 计算。

**阶段 2 退出规则：** 3 个代表性课程视频均能生成转写、OCR、关键帧/观察和来源时间；至少一个本地视频模型能够输出结构化候选；所有结果能由模型版本和时间轴重建。

#### 阶段 3：混合检索与问题解析

推荐采用两级检索，而不是每次把整段视频交给模型：

```text
问题解析/关键词与 Embedding 召回
→ PostgreSQL/pgvector 候选片段
→ 文本或跨模态重排
→ 仅对 Top-K 候选调用视频模型做精读
```

模型候选：

- **问题解析与答案草稿：** 选用与阶段 2 相同的本地语言/多模态模型，避免首版引入第二套不可控模型；若该模型的文本检索问答能力不足，可单独评测 Qwen3 系列文本模型，但必须把视频事实限制在检索证据内。
- **候选重排：** 优先使用 BGE/E5 类文本重排或跨模态 Embedding；只有在复杂问题上确实提高 Recall@K 时，才调用更大的 VLM。
- **长视频对照：** Qwen3-VL、InternVideo3 和 Gemini 可作为候选对照，但所有结果要经过统一的 Evidence 格式化和 tIoU 评测。

**阶段 3 退出规则：** 在开发评测集上记录 Recall@5、证据时间命中、无结果行为、查询延迟和模型调用次数；只有候选召回达标后，才进入时序推理和答案生成调优。

#### 阶段 4：时序事件与可解释推理

阶段 4 的模型职责应被限制为“自然语言问题解析、候选事件抽取和证据归纳”，不负责替代确定性时间计算：

- **首选：** 阶段 2 已通过基准的 VideoChat3-4B 或 Qwen3-VL 可部署版本。
- **长时域/复杂跨片段对照：** InternVideo3-8B-Instruct，重点评估远距离事件关联、时间 grounding 和证据验证。
- **云端能力对照：** Gemini 视频理解的静态/agentic 模式，仅在用户明确允许外部传输时启用；结果用于质量和成本对照，不作为本地默认依赖。
- **程序规则：** `before`、`after`、`overlap`、`duration`、`count` 必须由 `temporal` 模块根据带时间的事件计算；模型不能直接覆盖规则结果。

**阶段 4 退出规则：** 所有模型输出都能转为统一事件和证据；在边界、重叠、低置信度情况下可以拒答或返回不确定性；模型升级不会改变规则引擎的语义。

#### 阶段 5：端到端问答与 Demo

阶段 5 不新增一批模型。默认沿用阶段 2–4 通过验证的组合，并提供配置切换：

- `local_fast`：较小 ASR + PaddleOCR + VideoChat3-4B/Qwen3-VL 可部署版本，优先低成本和本地运行。
- `local_quality`：较高质量 ASR + 同一索引 + InternVideo3-8B 或较大 Qwen3-VL，优先复杂问题，但必须显示更高资源/延迟成本。
- `cloud_reference`：Gemini 视频理解，仅作为显式启用的参考路线，不默认上传用户视频。

Web Demo 只展示当前配置的模型和证据来源，不在页面层选择模型或拼接提示词。CLI/API 应允许在配置中选择 profile，并在结果中返回实际 profile、模型版本和处理耗时。

#### 阶段 6：质量、性能与交付

最终不按“最大模型最好”选择，而按以下顺序决策：

1. 是否能在独立集上满足答案、证据和正确拒答指标。
2. 是否能在参考硬件上满足问答延迟和视频处理耗时。
3. 是否能在许可、权重分发、数据传输和隐私边界上交付。
4. 是否能通过适配器替换、缓存和版本锁定保持可维护性。

阶段 6 至少报告 `model_profile`、模型/权重版本、采样参数、ASR/OCR 版本、是否使用外部服务和每阶段耗时。任何模型替换都应重新执行受影响的视频类型和问题类别评测。

#### 后续多类型视频场景的模型建议

下表用于产品化扩展，不是首版接入清单：

| 场景 | 优先组合 | 模型职责重点 | 首要评测 |
|---|---|---|---|
| `lecture` | faster-whisper/Whisper 或 FunASR + PaddleOCR + BGE-M3 + VideoChat3/Qwen3-VL 局部验证 | 术语、课件、章节、先后关系 | 中文 WER、OCR、证据 tIoU、答案正确率 |
| `meeting` | ASR + pyannote.audio 或 WhisperX 说话人/词级对齐候选 + 文本 Embedding + VLM 复核 | 谁说了什么、议题轮次、行动项 | 说话人归属、话题召回、时间证据；逐模型/权重核查授权与部署条件 |
| `film` | 场景检测 + 关键帧视觉特征 + Qwen3-VL/InternVideo3/VideoChat3 | 角色、跨场景事件、叙事关系 | 长距离 QA、角色一致性、事件定位 |

### 10.4 模块边界与最小接口

首版实现至少划分以下逻辑模块。模块可以先位于同一代码仓库或进程中，不要求立即拆成微服务：

| 模块 | 责任 | 最小输入/输出契约 |
|---|---|---|
| `media` | 校验媒体、读取元数据、场景切分、抽帧、音频提取 | 输入视频引用；输出视频元数据、片段和时间轴 |
| `speech` | 转写和语音片段对齐 | 输入音频/视频引用；输出带起止时间和来源的转写片段 |
| `vision` | OCR、关键帧观察、视觉向量 | 输入片段/关键帧；输出带时间、来源和置信度的观察 |
| `events` | 将观察规范化为事件并校验字段 | 输入观察；输出事件主体、动作、对象、时间范围和置信度 |
| `retrieval` | 全文、向量、时间过滤和重排 | 输入结构化问题；输出候选片段、观察、事件及相关性分数 |
| `temporal` | 计算先后、重叠、次数和持续时间 | 输入事件集合和时序问题；输出关系、计算结果和证据引用 |
| `answering` | 问题分类、证据选择、答案生成和拒答 | 输入问题与候选证据；输出答案、证据、不确定性和错误状态 |
| `orchestration` | 编排异步处理和问答流程、缓存、重试 | 输入任务/请求；输出可查询状态和结果引用 |
| `api/web` | 对外提供视频、任务、问答、证据跳转和删除能力 | 只依赖稳定的领域契约，不直接操作模型或文件系统细节 |

应用入口另分为：

| 入口 | 责任 | 约束 |
|---|---|---|
| `cli` | 提供可脚本化的导入、处理、状态、提问和评测命令 | 不复制领域逻辑；支持人读输出和稳定机器可读输出 |
| `api` | 为 Web Demo 和未来客户端提供统一 HTTP 接口 | 负责鉴权边界、请求校验、任务状态和错误映射；不直接承载模型实现 |
| `web` | 展示上传、状态、播放器、答案和证据 | 只调用 API；不在页面层实现检索、模型调用或时序规则 |

领域对象至少应复用第 6 节定义的 `Video`、`Segment`、`Observation`、`Event`、`Evidence` 和 `Answer`。时间统一为毫秒整数；跨模块不得用无法说明单位的浮点秒数或页面格式字符串作为主字段。

### 10.5 开发阶段、任务与阶段验收

阶段按照依赖关系推进。某阶段的“完成”表示该阶段退出条件满足并有可复现证据，不表示后续阶段已经完成。若阶段验收未通过，问题应登记到 `PROGRESS.md` 或 `TECH_DEBT.md`，不得通过跳过验收直接进入最终演示。

#### 阶段 0：项目基线与评测准备

**目标：** 建立可运行、可测量、可追踪的开发基础。

**任务：**

- 初始化仓库结构、环境文件、依赖锁定、Docker Compose 和基础 README。
- 固定至少 3 个可合法使用的代表性视频，覆盖语音/字幕、画面文字、可观察动作和基础时序关系。
- 建立至少 50 条问题样例的 JSONL 结构；为至少 20 条准备独立验收标注，包含标准答案、证据时间段、问题类别和是否应拒答。
- 建立最小评测脚本、样例数据脱敏/许可说明和组件许可证登记表。
- 定义 `Video`、`Segment`、`Observation`、`Event`、`Evidence`、`Answer` 的版本化数据契约。

**阶段验收：** 在新环境可以按照文档完成安装和最小测试；评测集可加载并通过模式校验；数据来源和许可证状态清楚；契约示例可以序列化/反序列化；没有真实密钥或未授权用户数据进入仓库。

#### 阶段 1：媒体导入与处理状态

**目标：** 建立可靠的视频输入、时间轴和异步任务骨架。

**任务：**

- 实现视频导入、格式/大小校验、元数据读取和存储适配器引用。
- 实现场景切分、关键帧抽取、音频提取，并保留统一的毫秒时间轴。
- 实现处理任务状态：等待、处理中、已就绪、失败；记录阶段、耗时和错误类别。
- 实现失败重试的边界、幂等任务标识和基础缓存策略。

**阶段验收：** 有效视频能完成导入并进入处理；无效视频能说明失败原因；同一视频不会因重复提交产生错误的跨视频结果；至少两个不同视频的片段时间戳可正确跳转；人为制造一个处理失败时能进入可诊断的失败状态。

#### 阶段 2：多模态观察与证据底座

**目标：** 从视频生成可追溯、可重建的语音、文字和画面观察。

**任务：**

- 接入 ASR，输出带起止时间的转写片段。
- 接入 OCR，输出文字、置信度、来源画面和时间映射。
- 对场景关键帧生成视觉特征和基础观察；保存模型/组件版本。
- 将所有观察与视频、片段、来源类型和置信度关联；支持按来源重建或删除。

**阶段验收：** 至少 3 个代表性视频能够生成可查询的多模态观察；每条观察可定位回原视频；缺失音轨、无文字或单个模型失败时系统不会伪造结果，并能标注来源不可用或处理不完整；核心输出通过契约校验。

#### 阶段 3：混合检索与问题解析

**目标：** 从问题中找到与时间和内容相关的候选证据。

**任务：**

- 建立 PostgreSQL/pgvector 数据表、全文索引、向量索引和迁移脚本。
- 实现问题规范化、关键词检索、向量检索、时间过滤和候选重排。
- 实现视频范围隔离、结果去重、证据来源保留和缓存键设计。
- 用固定评测集测量候选证据 Recall@K、查询延迟和无结果行为；记录基线而不是只观察最终答案。

**阶段验收：** 问题只能检索当前视频或明确选定的视频；候选结果都能回指原视频时间；开发评测集上有明确的 Recall@5、失败数和延迟记录；无相关内容时返回空/低置信候选而不是随机片段；重启服务后索引和迁移结果可恢复。

#### 阶段 4：时序事件与可解释推理

**目标：** 实现首版核心的事件结构化和确定性时序计算。

**任务：**

- 将观察规范化为事件，校验主体、动作、对象、时间范围和置信度。
- 实现 `before`、`after`、`overlap`、`duration`、`count` 等基础时间关系和边界条件。
- 实现问题分类：事实定位、先后关系、次数、持续时间和证据不足。
- 让规则计算优先于模型自由生成；由模型负责自然语言解析或证据归纳，并保留中间证据。

**阶段验收：** 固定样例中先后、重叠、次数和持续时间问题均能返回结构化结果和证据；事件重叠、边界不清、低置信度时能返回不确定性；单元测试覆盖空事件、同一事件、时间相等和跨片段等边界；不得通过无证据生成确定性答案。

#### 阶段 5：端到端问答、CLI/API 与用户界面

**目标：** 交付用户可使用的完整闭环。

**任务：**

- 实现视频列表/详情、处理状态、问答、答案证据和播放器跳转。
- 实现 `ingest`、`process`、`status`、`ask`、`evaluate` 等 CLI 命令，并确保核心链路脱离 Web Demo 可运行。
- 实现统一 API、错误响应、超时、幂等和删除接口。
- 将答案、证据、来源、不确定性和拒答状态分开展示。
- 实现视频及其衍生数据删除，并验证删除后的检索隔离。
- 使用 Playwright 或等价工具覆盖主流程和至少一个失败流程。

**阶段验收：** 在无 Web 页面时，按文档执行 CLI 的 `ingest → process → ask` 可以完成核心流程并输出结构化结果；Web Demo 可完成导入、等待处理、提问、查看答案、点击证据跳转和删除视频；至少两个视频之间没有串结果；无答案、处理失败和证据不足均有可理解反馈；CLI/API 和 Web 主流程测试可重复运行。

#### 阶段 6：质量、性能与交付加固

**目标：** 按 PRD 的统一口径确认首版是否达到交付标准。

**任务：**

- 在独立验收子集上测量答案正确率、证据命中率、正确拒答率和错误拒答率。
- 测量问答 p50/p95、10 分钟视频处理耗时、失败数、资源峰值和各阶段耗时。
- 完善结构化日志、依赖/模型版本记录、许可证核查、数据删除测试和安全检查。
- 修复阻断 P0 验收、安全、隐私或数据完整性的技术债务；对其余债务明确接受或排期。
- 生成可复现的启动、测试、评测和限制说明。

**阶段验收：** 第 8 节的首版完成定义全部满足；指标报告包含评测集版本、运行环境和组件版本；未达标指标和已接受债务被明确披露；在干净环境按文档可以启动并执行最小端到端流程。

#### 阶段 7：新增垂直视频场景验证（产品化后续，可选）

**目标：** 在首版课程视频闭环稳定后，验证一个有明确用户需求的新视频场景，不一次性扩展为“支持所有视频”。

**任务：**

- 根据目标用户和数据授权选择一个新类型（例如会议、产品演示或体育），暂时不同时做多个类型。
- 先建立该类型独立的代表视频、问题集、事件 schema 和证据标注规范。
- 采用手动选择 `VideoProfile`；复用统一 `Observation`、`Event`、`Evidence` 契约，为该场景组合专用采样、ASR/OCR、检测/跟踪和视频模型。
- 将新类型模型与课程视频现有基线分开评估；记录模型权重/代码版本、许可证、部署资源、数据流向、延迟和成本。
- 当手动策略和评测已稳定后，再评估是否需要自动类型识别；允许用户覆盖预测结果。

**阶段验收：** 新类型具有独立评测集和基线报告；新旧类型间无索引、缓存或证据串用；用户能看见/选择当前解析策略；新增策略对目标指标有可复现的改善，且通过安全、隐私和许可证核查。若没有足够数据或提升不明确，则停止扩展，不将该类型标为支持。

### 10.6 开发顺序与并行边界

推荐主线顺序为：

```text
阶段 0 评测/契约
    ↓
阶段 1 媒体导入与任务状态
    ↓
阶段 2 多模态观察
    ↓
阶段 3 混合检索
    ↓
阶段 4 时序推理
    ↓
阶段 5 API/界面闭环
    ↓
阶段 6 评测、性能与交付
```

阶段 7 是首版完成后的可选产品化分支，不阻塞课程项目交付；只有首版验收通过、目标场景和数据授权明确后才启动。

以下工作可以在主线具备契约后并行，但不能绕过依赖：

- 阶段 0 完成数据契约后，可以并行搭建后端骨架、前端静态页面和评测脚本。
- 阶段 1 的 API 状态契约稳定后，前端可以提前实现处理状态页面。
- 阶段 2 开始后，可以并行评测 ASR、OCR 和视觉模型，但只能在适配器边界内替换。
- 阶段 3 开始后，可以并行制作检索评测和 UI 证据卡片；没有候选证据契约时不实现最终答案展示。
- 阶段 4 完成基础规则后，才能接入开放式答案生成；模型生成不得成为时序规则的唯一实现。
- 阶段 7 必须在阶段 6 通过后启动，并从需求最明确、最容易取得合法评测数据的一个视频类型开始；自动路由在手动 Profile 有实测价值后再做。
- 性能和许可证检查从阶段 0 开始持续进行，不能留到最终演示前才首次检查。

不建议的顺序包括：先做复杂 UI 再确定证据数据结构；先选最大模型再围绕模型改产品；在没有评测集时反复调整提示词；在 CLI/API 核心闭环未通过前投入大量 Demo 视觉开发；在单体闭环未通过前拆分微服务或引入 Kubernetes。

### 10.7 阶段变更与选型复审规则

- 阶段内可替换实现，只要接口、用户行为和验收口径不变，并在进度记录中补充验证证据。
- 若候选组件在最小场景中连续无法满足质量、性能、许可证或数据边界要求，应记录淘汰理由并评估替代方案。
- 若改变模型或基础设施导致指标、资源、数据传输、部署方式或失败行为发生变化，应在 PRD 的变更记录中说明影响，并重新执行受影响阶段的验收。
- 若某项选型只为课程演示临时采用，必须标注“演示临时方案”和未来替换触发条件，不能默认为商业化基线。
- 选型决策不单独建立重复文档；必要的候选比较、实测数据和最终结论放在 `PROGRESS.md` 对应里程碑，长期约束只保留在本章。
